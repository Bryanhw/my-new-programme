## 0. 一句话

V5 是「校园拾光」**第一次从「广场」走向「人与人」的社交联动版**，同时把「匿名优先」推向极致：在守住匿名内容不可溯源这条命根子的前提下，首次引入**账号与账号之间**的轻互动——互相关注（V5-4）、评论里 @（需互相关注，V5-3）、双向私信 + 私信举报（V5-1）、邀请一起听歌（V5-2）；再叠加四个别人网站没有的**匿名情绪玩法**——写给那个洞号（并入 V5-1）、匿名翻牌告白墙（V5-5）、匿名抱抱反应（V5-6）、匿名漂流祝福（V5-7）；并修复同学反馈的**「无法删评」**现状痛点——作者可删除自己的评论（V5-8）。

一句话版本：**内容可以匿名，人和人之间可以互认，但匿名依然是匿名的**。

V5 同样守既有工程红线：纯静态前端、零构建；后端能力全部走 Supabase 增量迁移；每次改动守住回归基线并逐字节发版。

## 1. 项目总览

### 1.1 这是什么项目

「校园拾光」是面向大学生的校园生活分享网站：纯静态页面 + Supabase（Auth / Postgres / Storage）+ GitHub Pages 托管，零服务器、零构建。核心卖点一直是 **「想说什么就说，想匿名就匿名」**——每条内容可选匿名或署名，匿名帖/评论的作者 id 在接口层对前端**不可读**（列级授权 + definer 视图），匿名访客也与账号无关。

### 1.2 V5 想解决什么：从「广场」到「人」

前四个版本把「内容广场」做得很完整：发布、匿名洞号、城市圈、圈内热词、先发后审、举报、评论回复、生日祝福、密保改密。但这一切都是**人与内容**的互动——同学之间除了在帖子/评论里碰头，互相之间**没有直接的关系**：不能关注、不能私信、不能在评论里点名、不能约着一起听首歌。

V5 补上**「人和人」这一层**：让同学之间能建立轻量关系（互相关注）、能定向交流（私信）、能在内容里互相点名（@）、能约在一起听歌；并凭借平台既有的匿名能力，做出几个主流实名社交**给不了的**玩法（洞号来信、翻牌告白、匿名抱抱、漂流祝福）。

### 1.3 触碰的既有边界（本版明确点名，不悄悄越界）

`PROJECT_SCOPE.md` §5 原本明确「不做」的两件，V5 **主动、显式地触碰**（其余「不做」仍保持）：

| 既有边界 | V5 的处理 |
|---|---|
| 不做私信 / 群聊 / 聊天室 | **被 V5-1 触碰**：引入**双向私信**（仅点对点，不引入群聊/聊天室——群聊仍不做）；另支持「写给匿名洞号」 |
| 不做关注 / 粉丝 / 转发 / 好友体系 | **被 V5-4 / V5-3 触碰**：引入**互相关注**，并作为评论区 @ 的前置；转发/粉丝/好友体系仍不做 |
| 不做站内通知 / 邮件推送 | **被连带触碰**：@、私信、一起听歌、翻牌、漂流都需要轻量**站内提醒**入口（仅站内、不发邮件） |
| 单一广场、无分区 | **被 V5-2 触及**：新增「音乐专区」；仍是「一个站、几个专区」的轻分区，多校区/多租户仍不做 |

### 1.4 必须守住的核心红线（V5 一条都不能破）

1. **匿名不可被关联**：匿名帖/评论的作者 id 仍对前端不可读；V5 任何新身份标识（公开 UID）**不得回填**到匿名内容上，不得在匿名帖/评论卡片显示任何能反查作者账号的字段。
2. **图片路径不带身份**：`u/<16 位随机>/…` 与 `av/…` 的既有去标识路径不动；新功能（一起听歌封面等）沿用同一哲学。
3. **先发后审不放松**：帖子、评论的审核闭环（含举报三态回执）继续生效；新领域（私信、音乐专区、翻牌、漂流）的治理口径见各任务。
4. **低运维、零构建**：仍是纯静态 + Supabase 增量 SQL + Edge Function（如需）；不引 npm/构建/框架/JS 动画库；「实时」一律做成轻轮询/手动刷新，不铺服务器。
5. **既有护栏不松动**：颜色令牌、对比度棘轮、正文字号、卡片语法、版本串、逐字节发版全部延续；每个新里程碑必须自带对应新护栏。

### 1.5 最大的设计张力：需要「公开用户标识」，但不能动匿名的根

V5 的关注、私信、@、邀请、翻牌都要求**账号对账号**能被互相识别。但现状里数据库给作者的字段是 `author_id`（uuid）、**对前端不可读**（匿名红线地基），前端能看到的作者身份只有可重复的**昵称**与仅匿名帖可见的**洞号**。

因此 V5 引入一个**公开用户标识（公开 UID）**：

- **形态**：稳定、随机、与 `author_id` uuid **解耦**的公开短码（如 `@xh1234`，可含学校前缀做归属感）；`profiles` 加 `public_uid` 唯一列。
- **作用**：关注、私信、@、邀约、翻牌的共同身份锚点；昵称可改，公开 UID 生成后**不可改**（像洞号一样稳定）。
- **不破匿名**：公开 UID **只出现在账号身份语境**（用户主页、关注列表、私信对方、@ 高亮），**绝不**出现在匿名帖/匿名评论卡片上。匿名内容仍然只有「洞号 + 学校」两个可见身份，读者永远无法把匿名帖对应到某个公开 UID——这条写成护栏钉死。

**另一根关键原则：匿名与互认双轨并行。** 一个人可以同时有「公开账号身份」（昵称 + 公开 UID，能被关注/私信/@）和「匿名身份」（洞号，出现在匿名帖上）；这两轨**互不通**。任何功能都不得把「某洞号 → 某账号」的映射暴露给前端。

## 3. 里程碑 V5-4：互相关注（地基之上的第一块）

### 3.1 需求
- 每个登录用户有**公开 UID** 与公开主页（简介、关注数、关注的人）。
- 用户 A 可**关注** B、**取消关注**；双向都关注即**互相关注**。
- 互相关注是 V5-3（@）的前置；私信、邀约、翻牌可部分复用。

### 3.2 设计要点
- `profiles` 加 `public_uid text NOT NULL UNIQUE`（首登/首启生成，此后不可改）；`follows` 表 `(follower_uid, followee_uid, created_at)`，RLS：读公开、写限本人。
- 公开主页：复用 `profile.html` 或新增只读主页，展示昵称、学校、关注数、TA 关注的人。
- **匿名会话不可主动关注/被关注**（匿名身份不稳定，见 §13.4）。
- 护栏：匿名帖/匿名评论**绝不**携带公开 UID；关注公开可见不等于曝光匿名身份。

### 3.3 验收（草案）
- [ ] 两账号互相关注后双方主页显示「互相关注」；一方取消回到单向
- [ ] 公开 UID 稳定、唯一、不可改，昵称改动不影响关注关系
- [ ] 匿名帖卡片上找不到任何公开 UID / 关注入口（护栏验证）

## 4. 里程碑 V5-3：评论区 @（需互相关注）

### 4.1 需求
- 评论输入框可 **@ 用户**；满足**两人互相关注**才允许成功 @。
- 被 @ 者收到**站内提醒**，可跳回对应帖子/评论。
- @ 在评论里以可点高亮呈现（如 `@昵称(公开UID)`）。

### 4.2 设计要点
- 输入触发 @ 弹出**可 @ 候选**（仅「与我互相关注」的用户，保证前提落地）；选中插入 `@public_uid`。
- 库层：`comments` 新增可选 `mention_uid`；提交时校验「确实互相关注」，不通过拒绝并提示。
- 站内提醒 `notifications` 表（`user_uid, type, ref, read_at, created_at`），仅收件人可读。
- 匿名帖/评论本身**不可被 @**（没有可 @ 的公开身份）；被 @ 的只能是公开账号。

### 4.3 验收（草案）
- [ ] 互相关注者可互相 @，评论高亮正常、提醒可达；
- [ ] 非互相关注者 @ 被拒并明确提示；
- [ ] 匿名帖/匿名评论无可 @ 入口；提醒仅本人可见。

## 5. 里程碑 V5-1：私信 + 私信举报 + 写给那个洞号

### 5.1 需求
- 用户对另一用户**双向私信**（点对点），可举报不恰当私信；内容仅双方可见。
- **写给那个洞号**（站主已确认方案 A）：对某个匿名洞号发一封信，作者以洞号别名收信，双方都看不到对方真实账号。

### 5.2 设计要点
- 表 `direct_messages`（`room_id`（双方公开 UID 排序的会话键）/`sender_uid`/`recipient_uid`/`body`/`created_at`/`read_at`），RLS：仅 `sender_uid` 或 `recipient_uid`=本人可读写，第三方不可见。
- 会话列表页 + 对话页；不做 websocket，靠手动刷新/轻轮询。
- **私信是否需互相关注（决策点 §13.3）**：默认 **不要求**（开放私信，降低社交压力）；防骚扰备选「仅互相关注可私信」。
- **举报私信**：`message_reports` 表（举报人三态回执），审核台新增私信举报队列。
- **写给那个洞号的设计（关键，必须不破匿名）**：
  - 来信路由在**服务端**按洞号→作者完成，前端只见到「收信方 = 某洞号」；作者端以洞号作为会话别名呈现，收到的是一个**双向匿名会话**。
  - 站在「写给那个洞号」的人这边，看到收信方也只是洞号（不知道是谁）。
  - 也就是说这是一条**双方互不知身份**的私信通道——比普通私信更高一级的匿名。数据层用洞号做会话键，**不落**作者公开 UID，防反查；护栏钉死「洞号私信会话里不得出现任一方的公开 UID / 昵称」。
- **决策点 §13.2 已拍板方案 A**，故本里程碑直接包含该能力。

### 5.3 验收（草案）
- [ ] 私信双方各自只见自己与对方内容，第三方读不到（隐私探针）
- [ ] 私信举报提交 → 审核台可见 → 回执三态正常
- [ ] 写给洞号：发信人与收信人互不知身份；洞号私信会话里查无双方公开 UID / 昵称（护栏验证）

## 6. 里程碑 V5-2：一起听歌（音乐专区）

### 6.1 需求
- 新增**音乐专区**（轻分区/页面）：用户发布**音乐 app 或视频站链接**（网易云 / QQ 音乐 / B 站 / YouTube 等）+ 一句话 + 可**邀请某人一起听歌**。
- 「邀请」建立同听关系：被邀请方收到站内提醒，点开可与邀请人"同框听"（同一首歌/视频）。

### 6.2 设计要点
- 表 `music_posts`（`user_uid`/`platform`/`track_url`/`note`/`created_at`）+ `music_invites`（`music_id`/`inviter_uid`/`invitee_uid`/`accepted_at`）。
- **链接解析（决策点 §13.5）**：只接受**白名单平台**并解析出可嵌入/可跳转地址（如 B 站 BV、网易云歌曲 id）；非白名单或解析失败拒绝发布。
- 存储/隐私：封面沿用去标识路径；音乐帖随账号公开，但**邀请关系**仅双方可见。
- 「一起听」做**轻语义**：显示「🎧 在听这首歌的人」，邀请被接受双方卡片标记「一起听」；**不做**房间类实时音频同步（不引音视频服务器，守零运维）。

### 6.3 验收（草案）
- [ ] 白名单链接可发布并可跳转/内嵌；非白名单被拒并提示
- [ ] 邀请某人 → 对方收到提醒 → 接受后「一起听」成立，双方可见
- [ ] 邀请关系第三方不可见；音乐专区手机 390px 可用

## 7. 里程碑 V5-5：匿名翻牌告白墙（站主确认特色 ②）

### 7.1 需求
- 一个**双方匿名的告白**玩法：A 向 B（或对某公开账号）写一封告白信并「发送」，期间双方都以匿名呈现；只有当对方也愿意回应（互点「愿意」）时，两人**才相认**（彼此亮出对方/自己的公开账号）。
- 避免公开表白被拒的尴尬——被拒时只有发送者知道自己失败，对方轻轻略过即可。

### 7.2 设计要点
- `confessions` 表（`from_uid`/`to_uid`/`body`/`status`（pending / revealed / declined / ignored）/`created_at`）；`to_uid` 只在受理方视角可见，发送方以「发给某洞号/某主页」匿名呈现。
- 后台用公开 UID 锚定双方，但**页面前端全程匿名**；只有在 `revealed` 时才把双方公开身份互相点亮。
- 站内提醒：被告白者收到「有人给你留了封匿名告白，要不要看/回应」。
- 治理：可举报不恰当告白；先发后审思想沿用（或按轻治理）。

### 7.3 验收（草案）
- [ ] 匿名告白全程不暴露发送/接收方身份，直到互点「愿意」才相认
- [ ] 未回应/拒绝时只有发送方知情，无任何一面倒曝光
- [ ] 可举报；提醒仅本人可见

## 8. 里程碑 V5-6：匿名抱抱反应（站主确认特色 ④）

### 8.1 需求
- 在帖子/评论上加一种**比 🤍 更暖、且永远不公开是谁按的**轻反应「抱抱」；只显示计数，不显示名单。
- 这是 `PROJECT_SCOPE.md` §5 早已登记过的「抱抱」候选项，本版落地。

### 8.2 设计要点
- 复用/扩展现有 `likes` 收口思路：`post_hugs` 计数视图，只含 `post_id / hug_count / hugged_by_me`，**不含** `user_id`（同 likes 哲学，匿名情绪）。
- 一个用户对同一内容只能抱一次（幂等）；可取消。
- 无论内容匿名与否，抱抱计数都是非个人的「温暖氛围」信号。

### 8.3 验收（草案）
- [ ] 抱抱计数正确、幂等、可取消；界面不显示谁抱的
- [ ] 隐私探针确认抱抱视图无 `user_id`；无新读取通道

## 9. 里程碑 V5-7：匿名漂流祝福（站主确认特色 ⑥）

### 9.1 需求
- 城市圈内**每天随机一条匿名的晚安/早安祝福漂流**，限时读一次，营造同校温情。
- 复用既有城市圈数据与「圈内」语义。

### 9.2 设计要点
- 轻薄结构：祝福由账号用户发（可选匿名），系统当天在**同城市圈**内随机投放；每人每天限读一条、限时（如当日有效）。
- `drift_notes` 表（`user_uid`/`body`/`circle`/`created_at`/`pick_window`）；投放为服务端（Edge Function）或随机索引的只读查询。
- 读到的是一条**匿名祝福**（不显示发送者身份），收件可给反馈（抱抱/感谢计数）。
- 防刷：每人每天一条、分离出「未读/已读」状态。

### 9.3 验收（草案）
- [ ] 同圈用户当天能收到一条随机匿名祝福，一天一条、限时
- [ ] 祝福不暴露发送者身份；可轻回应（感谢计数）

## 10. 里程碑 V5-8：删除自己的评论（站主补充）

### 10.1 需求
- 同学反馈「发出去的评论删不掉」——补齐**作者可删除自己评论**的能力，修复现状痛点。
- 适用于署名与匿名评论：作者（提交者）都能删自己的评论。

### 10.2 设计要点
- 新增 RPC（如 `delete_comment(p_comment_id)`），在**服务端**校验 `auth.uid()` = 该评论提交者后删除；不信前端显隐（越权由后端把关）。
- 匿名评论同样可删：服务端按 auth.uid 定位提交者即可，无需暴露 author_id——正好复用匿名地基。
- 删除语义：被删评论就地显示「评论已删除」，其下回复一并折叠/隐藏，避免孤儿回复挂在已删评论上。
- 语义边界（站主 2026-11-11 已确认 §13.7）：帖子作者**不开放**删除别人在自己帖子下的评论——只允许站主经举报/审核队列处理（防滥用、防误伤）。

### 10.3 验收（草案）
- [ ] 评论作者（署名或匿名）可删自己的评论，删除后显示「评论已删除」、回复折叠；他人无删除入口
- [ ] 前端隐藏入口不可绕过：直接调 RPC 删他人评论被服务端拒绝（越权探针）
- [ ] 手机端 390px 删除入口可用

## 11. 红线（V5 明确不做）

- **不做群聊 / 群组 >2 人**（私信严格点对点；洞号信也是点对点）。
- **不做**粉丝/转发/好友图谱运营页；关注只有「关注/取消」两态。
- **不做**邮件 / 短信 / 推送通知（站内提醒只在站点内）。
- **不做**实时音视频房间（一起听歌是"共享 + 邀约"，不做服务器端播放同步）。
- **不动匿名地基**：匿名帖/评论不携带公开 UID；「洞号↔账号」映射永不暴露给前端；图片去标识哲学不变；先发后审不变。
- **不**把公开 UID 变成第二套登录凭证（不改认证模型）。
- **不**用公开身份污染匿名体验：凡匿名玩法，前端一律不渲染任一方的公开身份，直到守规则地「相认」。
- 既有护栏（颜色令牌 / 对比度 / 字号 / 卡片语法 / 版本串 / 逐字节发版）不因 V5 松动。
