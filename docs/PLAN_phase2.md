## 0. 一句话

Phase 1 解决的是「能跑起来」；Phase 2 解决的是**「同学愿意再来用，而且敢匿名用」**——
补互动、开圈层、把隐私边界从「能用」提到「经得起当面追问」。

本阶段的验收**不看写了多少功能，只看你实测 + 同学试用后的真实反馈**（第 4 节）。

## 1. 阶段目标

三条，按优先级：

1. **优化用户体验**：把 Phase 1 登记在案的遗留清单收干净（图片展示、卡片操作区、审核与被举报体验）。
2. **增加新功能**：增加互动能力（轻反应、话题标签、分享链接），并落地**同城大学圈**。
3. **增加安全与隐私配置**：把已经设计好的隐私收口真正落地，并让「匿名不可追溯」这句话经得起验证。

一句话版本：**先让用起来更顺手，再让人愿意留下，最后让每个同学都敢说真话。**

## 2. 这个阶段做什么 / 不做什么

**本阶段做**：图片展示三件套、卡片操作区、审核与被举报体验补完、轻反应、话题标签、分享链接、同城大学圈、学校字段规范化、稳定洞号 + `likes` 通道收口、发布频率限制、隐私回归验收。

**本阶段继续不做**（沿用 `PROJECT_SCOPE.md` 第 5 节的产品边界，不在本阶段重新讨论）：

- 私信 / 群聊 / 关注 / 粉丝 / 转发 / 好友体系；
- 原生 App、真实短信、实名认证；
- 富文本 / Markdown 编辑器；
- 站内通知 / 邮件推送；
- 广告 / 付费 / 会员；
- 评论区的逐条匿名（评论一律跟随账号或访客昵称署名）。

### 2.1 「同城大学圈」与现有范围边界的冲突及处理（已定：方案 B）

这一项**不能直接开工**，有两个硬障碍：

**障碍一：它撞上了已经写下来的边界。** `PROJECT_SCOPE.md` 第 5 节写着：

> 不做多校区 / 多租户 / 社区分区（一个站点、一个广场）

按字面理解，「同城大学圈」就是社区分区。要么改这条边界，要么换一种实现方式。

**障碍二：学校字段现在是自由文本，聚合不可靠。** `login.html:112` 的学校是**手输输入框**
（`type="text"`，`maxlength=40`，没有下拉、没有校验），数据库里 `public.profiles.school` 与
`public.posts.school` 都是 `text`（`posts.school` 还是**发布时的快照**）。这意味着
「××大学」「××大学 」「xx大学」「××大学（东区）」会被当成**四所学校**——
直接按这个字段分圈，圈里永远是碎片。

三种做法：

| 方案 | 形态 | 代价 |
|---|---|---|
| A. 真分区 | 每个城市 / 学校一个独立子广场 | 违背现有边界；每个圈都要单独有人，冷启动几乎必然失败 |
| **B. 同城筛（推荐）** | **仍是一个广场**，新增「城市 / 学校」维度做**筛选视图**：首页与广场加「只看同城」「只看同校」 | 小；内容池不分裂，冷启动靠现有内容；不违背「一个广场」的精神 |
| C. 只补数据不补功能 | 先把学校规范化做掉，圈层等功能留到有真实用户量 | 最小，但本阶段目标 2 就少一项 |

**已决定（2026-09-28）：走方案 B —— 同城 / 同校筛选视图。**

- 形态：**仍是一个广场**，只增加「城市 / 学校」维度的筛选，不产生独立子社区；
- 因此 `PROJECT_SCOPE.md` 第 5 节**保持原样**——「不做社区分区」依然成立（筛选不是分区）；
- A（真分区）与 C（只补数据）作为备选保留：若将来用户量足够、且有人明确要求「本校专属版面」，
  再回来评估 A，届时要正式修订第 5 节；
- **前置条件不变**：学校必须先规范化，否则筛选页会碎片化（任务 D2 → B5）。

## 4. 检测方法（本阶段的核心）

你给的验收方式是：**你自己测 → 邀请同学参与 → 请他们给反馈**。下面把它做成可重复的流程，
而不是"感觉还行"。

### 4.1 第一步：站主自测（功能走查）

电脑端 + 手机端各走一遍，逐项勾选：

- [ ] 1. 打开线上站点，主页正常；图片三件套生效（竖图不裁人、能看原图）
- [ ] 2. 发布署名内容 → 审核中 → 通过后广场可见
- [ ] 3. 「匿名进入」再发一条 → 通过后可见，**署名显示编号**（如「匿名 #771CEA」）且不露昵称 / 学校
- [ ] 4. 评论与回复：账号与匿名访客各一次，署名正确
- [ ] 5. 卡片「⋯」三个动作各一次；复制出的链接打开后能定位到该条
- [ ] 6. 轻反应计数正确；话题筛选、置顶各一次
- [ ] 7. 举报一条内容 → 「我的」出现回执；审核台处理 → 回执状态更新
- [ ] 8. 走通「被拒稿 → 看到原因 → 修改后重提」和「被下架 → 申诉 → 恢复」
- [ ] 9. 同城 / 同校筛选能筛出内容，且空结果有引导
- [ ] 10. 手机浏览器重复第 1、3、4、5 条

### 4.2 第二步：邀请同学试用

- **人数**：**5–8 位**（判定线取 ≥5，见 4.4），其中至少 3 位愿意隔几天再用一次（"愿不愿意回来"才是真信号）。
- **必须覆盖的路径**：至少 2 位走**匿名**、至少 2 位走**注册账号**；至少 1 位主动用一次同城圈。
- **怎么邀**：把链接直接发给同学，**不要先教怎么用**——你觉得"显然"的地方，正是要测的地方。
  只给一句：「随便发点什么，用完跟我说说哪里别扭。」
- **留痕**：截图或记下卡住的步骤（能复现的才叫反馈）。

### 4.3 第三步：收集反馈

**必答四题（1–5 分，5 最好）**：

1. 第一次打开，你知道怎么发一条吗？
2. 用匿名的时候，你心里踏实吗？
3. 你愿意再回来用吗？
4. （试了同城圈才问）你能一眼看出这是本校 / 本城的内容吗？

**开放两题**：

5. 哪一步最别扭？如果只能改一处，改哪里？
6. 有没有哪一刻让你觉得"我的隐私被暴露了"或"这里不安全"？

**匿名性小测（关键，用来验目标 2，不要提前解释这是在测隐私）**：
让对方看着广场，直接问「**你能看出来这条是谁发的吗？能猜出来吗？**」
——回答"看不出来"才算通过；只要有人能靠页面上的信息猜出来，就是隐私缺陷。

**记录模板**（照抄成一张表即可）：

| 日期 | 同学（代号） | 设备 | 走的路径 | 是否发布成功 | 四题分数 | 原文反馈 | 发现的问题 | 是否已修 |
|---|---|---|---|---|---|---|---|---|

> 要求：**先原样记录，再解释**。Phase 1 的经验是，把"同学卡在哪"和"我以为他卡在哪"
> 混在一起写，结论就没有价值了。

### 4.4 判定规则（已生效 · 默认值）

> 2026-09-28 已确认：**采用下表默认值**，即刻作为本阶段验收标准。
> 之后若要调整（例如试用人数规模变了），改这里并同步 §6 与文档版本号——**不要口头改判据**。

| 阶段目标 | 达标条件 |
|---|---|
| **用户体验：用户评价良好** | ≥5 位同学完成试用；第 1/2/3 题**平均 ≥4.0**；且**没有阻断级反馈**（阻断级 = 有人在没有你帮忙的情况下卡住、发不出来） |
| **隐私：访客个人隐私得到保障** | `privacy_probe.py` **34/0**；匿名性小测 **≥5 人全部**回答"看不出"；`likes` 通道已收口（D1） |
| **互动：增加更多互动功能** | 新增互动中**至少 2 项被真实使用过**（不含你自己测试）；同城圈筛选至少 1 位同学主动用过 |

**阻塞规则（优先级最高）**：只要有 **1 位**同学报告"能看出匿名内容是谁发的"，
**立刻停下所有新功能，先修隐私**，Phase 2 不推进。

**不达标怎么办**：第 1 题低 → 改引导与首次进入体验（不是加更多功能）；
第 3 题低 → 问题在"内容够不够看"，优先拉内容而不是做功能。
