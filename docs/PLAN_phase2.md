## 0. 一句话

Phase 1 解决的是「能跑起来」；Phase 2 解决的是**「同学愿意再来用，而且敢匿名用」**——
补互动、开圈层、把隐私边界从「能用」提到「经得起当面追问」。

本阶段的验收**不看写了多少功能，只看你实测 + 同学试用后的真实反馈**（第 4 节）。

## 1. 阶段目标

三条，按优先级：

1. **优化用户体验**：把 Phase 1 登记在案的遗留清单收干净（图片展示、卡片操作区、审核与被举报体验）。
2. **增加新功能**：增加互动能力（轻反应、话题标签、分享链接），并落地**同城大学圈**。
3. **增加安全与隐私配置**：把已经设计好的隐私收口真正落地，并让「匿名不可追溯」这句话经得起验证。

一句话版本：**先让用起来更顺手，再让人愿意留下，最后让每个同学都敢说真话。**

## 2. 这个阶段做什么 / 不做什么

**本阶段做**：图片展示三件套、卡片操作区、审核与被举报体验补完、轻反应、话题标签、分享链接、同城大学圈、学校字段规范化、稳定洞号 + `likes` 通道收口、发布频率限制、隐私回归验收。

**本阶段继续不做**（沿用 `PROJECT_SCOPE.md` 第 5 节的产品边界，不在本阶段重新讨论）：

- 私信 / 群聊 / 关注 / 粉丝 / 转发 / 好友体系；
- 原生 App、真实短信、实名认证；
- 富文本 / Markdown 编辑器；
- 站内通知 / 邮件推送；
- 广告 / 付费 / 会员；
- 评论区的逐条匿名（评论一律跟随账号或访客昵称署名）。

### 2.1 「同城大学圈」与现有范围边界的冲突及处理（已定：方案 B）

这一项**不能直接开工**，有两个硬障碍：

**障碍一：它撞上了已经写下来的边界。** `PROJECT_SCOPE.md` 第 5 节写着：

> 不做多校区 / 多租户 / 社区分区（一个站点、一个广场）

按字面理解，「同城大学圈」就是社区分区。要么改这条边界，要么换一种实现方式。

**障碍二：学校字段现在是自由文本，聚合不可靠。** `login.html:112` 的学校是**手输输入框**
（`type="text"`，`maxlength=40`，没有下拉、没有校验），数据库里 `public.profiles.school` 与
`public.posts.school` 都是 `text`（`posts.school` 还是**发布时的快照**）。这意味着
「××大学」「××大学 」「xx大学」「××大学（东区）」会被当成**四所学校**——
直接按这个字段分圈，圈里永远是碎片。

三种做法：

| 方案 | 形态 | 代价 |
|---|---|---|
| A. 真分区 | 每个城市 / 学校一个独立子广场 | 违背现有边界；每个圈都要单独有人，冷启动几乎必然失败 |
| **B. 同城筛（推荐）** | **仍是一个广场**，新增「城市 / 学校」维度做**筛选视图**：首页与广场加「只看同城」「只看同校」 | 小；内容池不分裂，冷启动靠现有内容；不违背「一个广场」的精神 |
| C. 只补数据不补功能 | 先把学校规范化做掉，圈层等功能留到有真实用户量 | 最小，但本阶段目标 2 就少一项 |

**已决定（2026-09-28）：走方案 B —— 同城 / 同校筛选视图。**

- 形态：**仍是一个广场**，只增加「城市 / 学校」维度的筛选，不产生独立子社区；
- 因此 `PROJECT_SCOPE.md` 第 5 节**保持原样**——「不做社区分区」依然成立（筛选不是分区）；
- A（真分区）与 C（只补数据）作为备选保留：若将来用户量足够、且有人明确要求「本校专属版面」，
  再回来评估 A，届时要正式修订第 5 节；
- **前置条件不变**：学校必须先规范化，否则筛选页会碎片化（任务 D2 → B5）。

## 4. 检测方法（本阶段的核心）

你给的验收方式是：**你自己测 → 邀请同学参与 → 请他们给反馈**。下面把它做成可重复的流程，
而不是"感觉还行"。

### 4.1 第一步：站主自测（功能走查）

电脑端 + 手机端各走一遍，逐项勾选：

- [x] 1. 打开线上站点，主页正常；图片三件套生效（竖图不裁人、能看原图）
      —— **2026-10-01 站主人眼验收通过**：第一轮反馈「竖图两侧留白太大」，当日用「同一张图的模糊衬底
      铺满展示盒」修好，站主强刷复看后确认**可以收尾**（`0a8b103` / 留痕 `21fea17`）。
- [ ] 2. 发布署名内容 → 审核中 → 通过后广场可见

- [ ] 4. 评论与回复：账号与匿名访客各一次，署名正确
- [ ] 5. 卡片「⋯」三个动作各一次；复制出的链接打开后能定位到该条（**若那条已下架或更早，

- [ ] 7. 举报一条内容 → 「我的」出现回执；审核台处理 → 回执状态更新
- [ ] 8. 走通「被拒稿 → 看到原因 → 修改后重提」和「被下架 → 申诉 → 恢复」
- [ ] 9. 同城 / 同校筛选能筛出内容，且空结果有引导
- [ ] 10. 手机浏览器重复第 1、3、4、5 条
- [ ] 11. 发布页「今日一问」：点「写这个」把话题带进正文（已写的字不被覆盖）；**隔天再看一眼，
      换了一句**（同一天刷新不该变）
- [ ] 12. 话题标签：发布时挑 1–3 个话题发出（挑第四个会被拦住，并说明）；广场顶部出现筛选条、

> 但「手机上那一块会不会太高」只能看真机。

### 4.2 第二步：邀请同学试用

- **人数**：**5–8 位**（判定线取 ≥5，见 4.4），其中至少 3 位愿意隔几天再用一次（"愿不愿意回来"才是真信号）。
- **必须覆盖的路径**：至少 2 位走**匿名**、至少 2 位走**注册账号**；至少 1 位主动用一次同城圈。
- **怎么邀**：把链接直接发给同学，**不要先教怎么用**——你觉得"显然"的地方，正是要测的地方。
  只给一句：「随便发点什么，用完跟我说说哪里别扭。」
- **留痕**：截图或记下卡住的步骤（能复现的才叫反馈）。

### 4.3 第三步：收集反馈

**必答四题（1–5 分，5 最好）**：

1. 第一次打开，你知道怎么发一条吗？
2. 用匿名的时候，你心里踏实吗？
3. 你愿意再回来用吗？
4. （试了同城圈才问）你能一眼看出这是本校 / 本城的内容吗？

**开放两题**：

5. 哪一步最别扭？如果只能改一处，改哪里？
6. 有没有哪一刻让你觉得"我的隐私被暴露了"或"这里不安全"？

**匿名性小测（关键，用来验目标 2，不要提前解释这是在测隐私）**：
让对方看着广场，直接问「**你能看出来这条是谁发的吗？能猜出来吗？**」
——回答"看不出来"才算通过；只要有人能靠页面上的信息猜出来，就是隐私缺陷。

**记录模板**（照抄成一张表即可）：

| 日期 | 同学（代号） | 设备 | 走的路径 | 是否发布成功 | 四题分数 | 原文反馈 | 发现的问题 | 是否已修 |
|---|---|---|---|---|---|---|---|---|

> 要求：**先原样记录，再解释**。Phase 1 的经验是，把"同学卡在哪"和"我以为他卡在哪"
> 混在一起写，结论就没有价值了。

### 4.4 判定规则（已生效 · 默认值）

> 2026-09-28 已确认：**采用下表默认值**，即刻作为本阶段验收标准。
> 之后若要调整（例如试用人数规模变了），改这里并同步 §6 与文档版本号——**不要口头改判据**。

| 阶段目标 | 达标条件 |
|---|---|
| **用户体验：用户评价良好** | ≥5 位同学完成试用；第 1/2/3 题**平均 ≥4.0**；且**没有阻断级反馈**（阻断级 = 有人在没有你帮忙的情况下卡住、发不出来） |
| **隐私：访客个人隐私得到保障** | `privacy_probe.py` **37/0**；匿名性小测 **≥5 人全部**回答"看不出"；`likes` 通道已收口（D1） |
| **互动：增加更多互动功能** | 新增互动中**至少 2 项被真实使用过**（不含你自己测试）；同城圈筛选至少 1 位同学主动用过 |

**阻塞规则（优先级最高）**：只要有 **1 位**同学报告"能看出匿名内容是谁发的"，
**立刻停下所有新功能，先修隐私**，Phase 2 不推进。

**不达标怎么办**：第 1 题低 → 改引导与首次进入体验（不是加更多功能）；
第 3 题低 → 问题在"内容够不够看"，优先拉内容而不是做功能。

### 第 20 轮（2026-10-13）分享直链的兜底：那条不在这批里时，按 id 单独问一次

- **起因**：站主点开分享链接，看到第 19 轮那句「分享链接里的那条不在这批内容里 —— 可能已经下架，
  或者比最近加载的 50 条更早」。顺着这句查下去，定位到两件事：
  1) **那句提示本身不诚实**：把两个完全不同的原因（下架 / 更早）并成一个猜测，用户没法自救；
  2) **B4 的取数范围天生不够**：只在「已加载的这批」（最新 50 条）里找，等数据长到 50 条以上，
     更早的帖子用分享链接**必然**找不到。
- **排查过程（证据都留着）**：
  - 用匿名只读接口核对线上：`posts` 表里匿名可见的**总共只有 10 条**，那条 id 就是最新的一条
    （`status=approved`）—— 所以「比最近加载的 50 条更早」在当前数据量下**根本不成立**；
  - 真浏览器复现：本地起的服务与线上页面逐字节相同，用**同源 iframe** 跑真实 `feed.html`，
    把 `#notice` 的文字读回来 —— 真实 id 打开是「已经高亮」（10 张卡片、1 条高亮），
    换一个不存在的 id 才复现出站主看到的那句；
  - 把**圈子那条路径整条测掉**：12 个圈子逐个选中打开分享链接，全都能找到并高亮；连把
    「只看本圈」勾上（卡片从 10 张掉到 1 张）也仍然高亮 —— 因为 `onlyCircle()` 读的是复选框的
    **当前状态**，而分享链接是「全新打开」，那一刻它必然是未勾选的；

### 第 21 轮（2026-10-13）「今日一问」：发布页替他起个头（C1）

- **要解决的问题**：新用户最大的门槛不是「不会用」，而是**「不知道写什么」**。发布页原先只有一个
  空白的正文框，光标一闪一闪地等人。这一轮在正文框上方放一句**会按天轮换**的话题，点一下就能
  带进正文 —— **起个头，不强迫**（爱写别的照样写）。
- **做法（纯前端，零迁移、零新依赖）**：
  - `post.html`：正文框上方加一条 `.daily-q` 提示条（`今日一问` 小标签 + 话题 + 「写这个」按钮），
    在 HTML 里就带 `hidden`，**脚本算好今天那句才显出来** —— 脚本没跑起来不会留一个空壳；
  - `post.js`：`DAILY_QUESTIONS` 共 **14 句**校园味的话题（图书馆哪层最安静 / 食堂哪道菜值得排队 /
    宿舍楼下那棵树你注意过吗 …），`questionOfTheDay()` 用**本地日期的天数序号**取模：
    同一天恒定、跨天换一句、轮完从头来；**没有 `Math.random`**（不然刷新一次就变一句，那就成了
    抽奖而不是「今日一问」）；
  - 点「写这个」：正文**空着就写进去**，**已经在写就接在后面另起一行**（`replace(/\s+$/, "")` +
    `"\n"`），光标落到末尾、字数计数跟着更新 —— **绝不覆盖人家自己写的字**；
  - 按钮是 `type="button"`：它在 `<form>` 里，默认类型会**直接提交帖子**，这一条专门有护栏盯着；
  - 样式跟着既有的卡片语言走（软底 + 细边 + 圆角），窄屏 420px 以下换行，不把话题挤成一条竖线。
- **红线复核**：**零网络请求、零本机存储、零新增读取通道**（这段代码里连 `fetch(`/`from(`/
  `localStorage` 都不许出现），不碰审核流程，不新增页面。
- **护栏**：静态检查 +10 条、运行测试 +8 条（详见第 5 节）。运行测试里最实的一条是
  **「今天是哪一句」由 Python 按同一套本地天数算法重算一遍**，再和页面显示的对齐 ——
  轮换公式不是「信它」，是**核对它**。
- **基线**：`static_checks` 750/0 → **760/0**、`run_tests` 772/0 → **780/0**。
- **仍未由人眼确认的部分**：提示条在真机上的观感（小标签和「写这个」按钮的轻重、窄屏换行好不好看）、
  以及那 14 句话题**读起来像不像同学会想回答的话** —— 文案好坏只能由人判断，交给第 4.1 节
  站主自测清单第 11 条。

### 第 22 轮（2026-10-13）话题标签：分享可以带 #话题 了（C3 / r18 的 B2）

- **要解决的问题**：广场只有「最新」一条时间线，看什么全凭运气。给分享加一组话题，
  让「我现在只想知道食堂有什么」变成一次点击。
- **为什么是固定八个**：让同学自己造词，标签会碎成一片谁也看不懂的东西（#好吃 #美食 #干饭
  #今天吃了什么）。所以 `app.js` 里写死一份列表 —— **#食堂 #图书馆 #晚霞 #emo #求组队 #学习
  #运动 #随手拍** —— 发布页的 chips、广场的筛选条、卡片上的标签**都从它来**，迁移 SQL 里也必须
  出现同样的字（静态护栏盯着这件事：改列表就得两边一起改）。
- **改动**：
  - **迁移** [`supabase-topics.sql`](supabase-topics.sql)（+ [`-flat`](supabase-topics-flat.sql)
    粘贴版）：`posts.topics text[] not null default '{}'` + CHECK（`cardinality(topics) <= 3`
    且 `topics <@ array[...]` 只允许那八个）+ gin 索引 + `notify pgrst` 刷新表结构缓存。
    **由站主在 SQL Editor 执行一次**（本机没有 `service_role`，也永远不会有）。
  - `app.js`：`TOPICS` / `TOPIC_LIMIT` / `normalizeTopics()`（丢野词、去重、截三个）；
    `createPost()` 收 `topics` 并在插入时带上；卡片渲染出 `#话题` 链接。
  - `post.js` + `post.html`：正文框下方一排 chips（最多三个，满了直说而不是静默丢掉），
    发帖后若话题没带上，会明说一句「话题这次没带上 —— 站点的标签功能还没开启」。
  - `feed.js` + `feed.html`：`?topic=` 与筛选条；筛选**在已加载的那批上做**（不发新请求、
    不新增读取通道）**，且没选话题时完全不过滤** —— 无标签的分享仍在「全部」里，

### 7.3 P2（安全与稳健，需要迁移或更谨慎）

**2-1 全站没有 CSP** —— 优势：能挡一部分 XSS / 恶意注入。劣势：GitHub Pages **给不了响应头**，
只能用 `<meta http-equiv>`（覆盖能力本来就弱）；本站有内联脚本与内联样式，真要收紧就得加 `'unsafe-inline'`
（等于白做）或者把内联全搬出去（改动大、回归面大）。**结论：只做「不影响功能」的那几条**（如 `object-src 'none'`），
别把它当成一道墙。证据：**待复核**。

**2-2 全站没有限流**（含 `reset-password` 可被用来跨账号试密保答案）—— 优势：抗刷帖、抗撞库；
「密保答案可被跨账号试」这条是**账号安全**问题，不只是垃圾内容问题。劣势：Postgres 触发器在写入关键路径上，
实现粗糙会误伤正常用户；跨账号撞库要在 edge function 里加节流（**要重新部署函数**，
属于「需要站主执行」的那类）；阈值定错会造成「我发不出帖」的投诉。**动手前必须先把现状确认清楚**。证据：**待复核**。

**2-3 上传校验可绕过**（`file.type` 为空串时会跳过类型判断；桶的写策略只校验 `bucket_id`，没有路径 / MIME / 体积闸门）
—— 优势：把闸门放到数据库侧，前端怎么绕都没用；能挡「伪装成图片的可执行内容 / 超大文件」。劣势：
在 `storage.objects` 策略里校验 MIME / 体积要读 `metadata`，写法绕、易错；**必须用真实上传做回归**，
否则可能把正常上传一起堵死（这类「安全改动把功能搞坏」的事故最常见）。证据：**待复核**。

**2-4 接口报错把 `err.message` 原样显示给用户** —— 优势：用户不再看到英文技术报错（观感 + 少泄露一点内部结构）。
劣势：**排障会变难** —— 所以做法应是「界面给人话、原始错误打 `console`」，而不是把错误吞掉。
证据：**待复核**。

**2-5 会话落在 `localStorage`，退出登录的清理没有证据** —— 优势：共用电脑 / 借同学手机时更干净。
劣势：改认证路径**风险高**（最坏情况是把人踢下线或登不上），而且要先确认 supabase-js 的真实行为，
**不能凭猜改**。建议只做「退出时显式 `signOut` + 清掉本站写入的 key」这一件事，并补一条测试。证据：**待复核**。

**2-6 `my_posts` 视图未设 `security_invoker`、`profiles.phone` 明文存储** —— 优势：视图按调用者权限执行更稳；
`phone` 是联系信息，明文意味着一旦数据面被读就走漏。劣势：改视图要重定义 + 重授权，**有前车之鉴**

收益低、牵连大。**建议：只记账，不动。** 证据：**待复核**。

—— 优势：可维护性、降低「改 A 坏 B」的概率。劣势：**纯重构、用户零收益、回归面最大**
（`app.js` 里大量 DOM 逻辑与兜底路径），而且护栏数量巨大，重构期间很容易变成「为了绿而绿」。
**建议：不专门做，下次要动某一段时顺手拆。** 证据：**已复核**（行数为实测）。

**3-7 审核台可以加批量操作 / 搜索 / 驳回时落个原因** —— 优势：站主每周审帖更快，尤其帖量上来以后。
劣势：审核台是**仓库外的本机单人工具**，收益只属于站主一人；每加一个功能都要维持它的自检全绿（现在 115/0）。
证据：**待复核**。若要与 1-4 一起做，驳回原因**正好可以一举两得**（审核台录入 → 站内可见）。

**3-8 没有线上监控** —— 优势：白屏、接口 500 这类「没人会来反馈」的问题能被人知道。劣势：要接第三方服务
或自己做轮询 + 通知渠道，引入外部依赖与成本；本站体量小。**折中**：每周手动跑一次现成的探针（已经有这个习惯）。
证据：**已复核**（无任何监控配置）。

### 7.5 明确不建议（或需站主另行拍板）

- **真·全站搜索**：1-1 已在第 30 轮修掉（广场能一路翻到最早一条），所以「只会搜到那 50 条」这个技术障碍没了 ——
  但**下面这条反对意见一条都没变**：搜索会新增 `?q=` 面与全文索引，
  等于**给匿名内容加了一个新的关联入口**（同一个人用同一批词能串出他的多条匿名帖），与 D1 / D7 的方向相反。
- **帖子详情页**：`?id=` 直链就是新的匿名关联面 —— 一条链接可以把人精确引到某一条匿名帖，还能被反复分享、被爬。
  第 20 轮的**分享直链**已经满足了「我想把这条发给朋友看」，再进一步收益小、风险大。
- **通知 / 关注粉丝 / 自建后端 / 短信邮件**：与 `PROJECT_SCOPE.md` 第 5 节和 `PLAN_phase2.md` 第 2.1 节的边界直接冲突，
  不是「优先级低」而是**不在范围内**。

3. **1-4 A3 / A4** —— 它是唯一一条「不做就会伤到主动发帖的人」的，也是唯一能让审核台顺带受益的。
